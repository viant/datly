# Generated mutation recovery

A generated writer may declare an optional root lifecycle hook:

```go
func (*Lifecycle) Recover(ctx context.Context, input *Input, output *Output,
    outcome handler.MutationOutcome) (handler.Recovery, error)
```

Here `handler` is `github.com/viant/datly/runtime/handler`. Contracts remain
generated by `datly transcribe`; the authored hook decides business ownership.
No new DQL directive, predicate DSL, SQLX dependency in xdatly, or manual writer
handler is required. The existing lifecycle declaration selects the hook type.
The compiler validates the optional method signature.

## Evidence and admission

`MutationOutcome` includes the detached xdatly transaction Outcome plus a
Mutation result: Operation, Table, Records, Affected and Error. Counts describe
actual execution, including zero affected rows; they do not prove ownership
before transaction completion. `Attempt` starts at zero and `RetryLimit` is one.

The runtime admits recovery only for one finished root finalizer, one known
database unit, one queued row operation and one executed record. It rejects
batches, queued siblings, child finalizers, unrelated database errors, handler
validation failures, additional completion diagnostics, caller-owned/pending
transactions, and uncertain/mixed/partial completion.

Eligible cases are a committed zero-row operation, or a confirmed rollback of
a SQLX duplicate-key failure, native guarded mutation Conflict, or driver-coded
transaction contention. Contention includes SQLite busy/locked snapshots, MySQL
deadlock/lock-wait errors and SQLSTATE 40001/40P01; message text alone is insufficient. Other cases
keep their existing behavior. The hook must distinguish relevant unique-key
losses from unrelated uniqueness failures and verify any adopted winner through
the generated typed reader or fresh Current data.

## Decisions

- `RecoveryNone` preserves the original result/error.
- `RecoveryAccept` returns the output corrected by the hook, suppressing an
  eligible operation error for the public result. Actual transaction evidence
  remains unchanged and does not become a commit.
- `RecoveryRetry` requests one native replay with fresh Current/dependency reads
  in a new owned invocation. A second retry request fails explicitly. On that
  last attempt a business hook may instead reload and accept a stored winner.
- A hook error or panic remains a failure; it cannot discard original evidence.

Replay captures transport source values through the existing canonical Bindly
plan before input/business initialization. It preserves omitted/null/zero
presence and revalidates transformed request inputs. Trusted typed BoundInput
uses native shape cloning of request fields and presence markers; read indexes,
Current, injected services and derived controls are not carried into a retry.

Each attempt is finalized once. A superseded attempt receives its actual
transaction evidence plus an explicit retry error, preventing success publication
from that attempt. The Completion observer runs for the terminal attempt.
An accepted rolled-back attempt retains rollback evidence in its finalizer and
observer even though its corrected public result succeeds. Winner adoption
does not prove this caller created or committed the winner.

Application callbacks that perform external side effects must account for a
possible second attempt. Recovery does not silently make those callbacks
idempotent. Never issue manual SQL, replay caller transactions, publish on Queue,
or infer recovery safety from an error string or a nil return alone.

## Verification

Native tests cover actual ignored-insert counts, guarded misses, duplicate
failures and unexecuted siblings, detached reporting, admission boundaries,
bounded attempts, fresh dependencies, original request facts, typed presence,
finalizer disposition and terminal observer behavior. Application parity and
cross-connection concurrency remain required for each component that opts in.
